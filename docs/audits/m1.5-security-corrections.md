# M1.5 security corrections

Corrections demonstrated by the independent source review. Each entry states the
defect, impact, smallest fix, regression test and verification result. No
unrelated refactoring or M2 work was performed.

## D1 + D3 — `NULQ-FS-002` escalated non-root authority and overstated confidence

**Source:** `internal/rules/filesystem/world_writable.go`.

**Defect.** Every executable with SUID or SGID directly inside a world-writable
non-sticky directory produced HIGH with HIGH confidence. The owner UID was not
part of the condition. A user-owned SUID binary therefore looked like root
exposure, and a root-owned SGID binary looked like root although it grants only
a group. Confidence was HIGH even though no execution or consumer was observed.

**Impact.** False HIGH findings on delegated, non-root authority; inflated
confidence for a conditional exposure. This directly violated the project's
"presence is not vulnerability" rule.

**Fix.**

- Precompute only **root-owned, executable SUID** files (`owner_uid == 0`,
  `setuid`, any execute bit) as replaceable root candidates.
- Escalate only when such a file is a direct child of the writable directory.
- Keep MEDIUM for all other world-writable non-sticky directories.
- Set confidence MEDIUM and state that execution is not observed.
- Explain that user-owned SUID and root SGID do not grant root.

**Regression tests.**

- Unit matrix: direct root SUID → HIGH; nested root SUID → MEDIUM;
  non-executable → MEDIUM; user-owned SUID child → MEDIUM; root SGID child →
  MEDIUM.
- Lab: `FS-004` (HIGH direct root child), `FS-019` (nested, MEDIUM),
  `FS-021` (user-owned SUID, MEDIUM, absent HIGH), complete inventories.

**Verification.** `go test ./internal/rules/...` 0; lab 32/32 after all fixes.

## D2 — `NULQ-FS-002` missed user-owned sticky directories

**Source:** the same rule skipped `sticky` unconditionally.

**Defect.** Sticky semantics restrict unlink/rename to the file owner, directory
owner or root. A `1777` directory owned by the assessed user lets that user
remove a root-owned SUID entry. Skipping all sticky directories was a false
negative.

**Impact.** A genuine root code-replacement path could be hidden by the sticky
bit while the assessed user owns the directory.

**Fix.**

- Read the assessed EUID from the execution-context observation.
- For sticky directories, continue only when the directory owner equals the
  assessed EUID; otherwise the sticky bit protects entries and the directory is
  skipped.
- Emit HIGH only when such a directory directly contains a root-owned SUID
  executable; a user-owned sticky directory without one is not reported.

**Regression tests.**

- Unit: root-owned `1777` + root SUID child → no finding; user-owned `1777` +
  root SUID child → HIGH.
- Lab: `FS-022` uses a `1777` directory owned by uid 10001 with a root SUID
  child and requires HIGH with MEDIUM confidence; `FS-001`/`FS-002` still prove
  a root-owned sticky directory stays silent.

**Residual judgment.** Execution of the replaced binary is still not observed.
HIGH is retained as an exposure because root SUID semantics make execution
root-authoritative and direct replaceability is observed; confidence is MEDIUM.

## D4 — `NULQ-SYS-002` treated unknown MAC state as disabled

**Source:** `internal/rules/system/mac.go`.

**Defect.** If a MAC module appeared in the kernel LSM list but its state file
was absent or unreadable, `macAdvertised` was true while `enforcing` stayed
false, so the generic "module present but not enforcing" LOW finding fired.
LSM-list membership is not proof of enforcement, but neither is a missing state
file proof of disablement. `smack` has no state collector at all.

**Impact.** False "no MAC enforcing" findings on systems with an unreadable or
unsupported state observation.

**Fix.**

- Track advertised module names separately from enforcement.
- Mark state unavailable when AppArmor/SELinux is advertised without a usable
  state observation, when SELinux detail is empty/unrecognised, or when smack is
  advertised.
- Suppress the generic finding while state is unknown. A permissive SELinux
  finding still reports that specific state; an enforcing module in another
  module still suppresses the generic finding.

**Regression tests.**

- Unit: advertised AppArmor without a control → no finding; SELinux advertised
  with no detail → no finding; smack advertised → no finding; mixed
  AppArmor-enforcing + SELinux-permissive → exactly one MEDIUM permissive
  finding; AppArmor alone → silent.

**Verification.** `go test ./internal/rules/system` 0; SYS-002 lab scenario still
passes.

## D5 — Validator could silently ignore unasserted findings

**Source:** `internal/lab/validate.go`, `internal/lab/manifest.go`.

**Defect.** Unexpected findings were computed only inside a scenario `scope`.
Baseline, fixtures and PATH scans had no scope covering `NULQ-SYS-001`, and the
discovery scan had no findings scope, so 16 findings were neither asserted nor
allowed while the summary reported `unexpected_findings: 0`. The prior
"46 total / 45 asserted / one extra sysctl" explanation was wrong.

**Impact.** A genuinely unexpected finding outside a convenience scope could
pass the gate; the release counters were misleading.

**Fix.**

- Add `allowed_findings` to manifest expectations for expected-but-unasserted
  findings (kernel-dependent sysctls; discovery's standard SUID inventory).
- Build a per-scan accounted set from every supported scenario's positive and
  absence matches plus allowed patterns.
- Report any remaining finding in `findings.unaccounted`, count
  `summary.unaccounted_findings`, and fail `summary.passed`.
- Keep `scope` only as a localiser for its own unexpected check.

**Regression tests.**

- `TestUnaccountedFindingFailsWithoutScope` — an extra finding with no scope is
  unaccounted and fails.
- `TestAllowedFindingIsAccounted` — an explicitly allowed finding passes.
- Existing duplicate, dangling-evidence and evidence-free tests remain.

**Verification.** Final lab: 54 findings = 38 asserted + 16 allowed + 0
unaccounted; `unaccounted_findings: 0`.

## D6 — Historical report contained a false finding-count explanation

**Source:** `docs/audits/m1.5-final-engineering-report.md`.

**Defect.** The report claimed 46 total, 45 asserted and one additional sysctl.
Independent reconstruction found 16 unasserted findings. The equality 46 − 45
was coincidental, and `expected_findings` is a sum of assertion minima, not a
distinct total.

**Fix.** The historical report is marked superseded and points to this review.
The current explanation is in `m1.5-independent-source-review.md` §8. No counter
was altered to hide the discrepancy; the validator now exposes it.
