## 1. Executive summary

M1.5 is complete. The independent audit found and corrected five real
correctness defects that previous tests had not caught:

1. `NULQ-FS-003` reported a writable PATH directory, an empty PATH element and
   a relative entry as **HIGH** without observing any privileged consumer.
2. `NULQ-FS-001` reported non-standard location, non-root ownership and inert
   non-executable set-owner-ID bits as privileged exposure.
3. `NULQ-FS-002` escalated any world-writable PATH directory to **HIGH** by
   membership alone and matched privileged executables in nested subdirectories
   by string prefix.
4. `NULQ-SYS-002` could report "no MAC enforcing" while AppArmor was enforcing,
   because a permissive SELinux finding cleared the overall flag.
5. Coverage did not report deliberately excluded mounts or distinguish timeout
   and cancellation classes, and the laboratory validator did not detect
   duplicate findings or dangling evidence.

A sixth defect was found in the laboratory tooling: `make lab-build` could exit
141 (SIGPIPE) after a successful build because `nulq version | head -n 1` closed
the pipe.

After correction, the laboratory reports **30/30 supported scenarios passed, 5
unsupported, 0 missing, 0 unexpected, 0 severity/confidence mismatches, 0
duplicate findings, 0 dangling evidence, 5/5 schema-valid reports**. Host
safety and cleanup guarantees were verified behaviourally.

## 5. Severity and confidence corrections

### 5.1 NULQ-FS-003: PATH writability HIGH → LOW

- **Original problem:** empty, relative and writable PATH entries were HIGH.
- **Evidence:** the rule consumed only PATH and execution-context observations.
  No privileged consumer, sudo `secure_path`, service environment or command
  shadowing was observed. The implementation fabricated the consumer in its
  impact text.
- **Change:** every case is LOW; impact and limitations state that escalation is
  not established. Metadata default changed to LOW. PATH ordering is never an
  escalation factor.
- **Regression tests:** unit cases for empty/relative/root-owned/self-owned/
  non-writable/missing entries; scenarios FS-011, FS-014, FS-017 (late entry),
  FS-018 (other-owned, not writable), INV-002.

### 5.2 NULQ-FS-001: location, ownership and inert bits

- **Original problem:** non-standard location and non-root ownership were
  MEDIUM; standard inventory was LOW; a SUID bit without execute was treated as
  privileged.
- **Evidence:** location does not alter permissions; a user-owned executable
  runs with the caller's credentials; the kernel ignores SUID without execute
  (SGID on a non-executable regular file means mandatory locking). Only a
  writable root-owned executable crosses into root.
- **Change:** INFO for standard inventory and inert bits; LOW for non-standard
  location, non-root owner or self-owned writable; MEDIUM for another
  non-root account's writable executable; HIGH only for writable root-owned.
  Evidence now includes owner UID.
- **Regression tests:** eight-case unit matrix; FS-005 (LOW), FS-006 (LOW),
  FS-007 (LOW, absent MEDIUM/HIGH), FS-009 (INFO), FS-020 (inert INFO, absent
  HIGH/MEDIUM), INV-001/002.

### 5.3 NULQ-FS-002: PATH escalation and nested prefix matching

- **Original problem:** any world-writable PATH directory became HIGH, and a
  privileged executable anywhere below the directory matched by prefix.
- **Evidence:** PATH membership alone does not make a regular file replaceable
  by a privileged consumer; directory write permission permits unlink/rename
  only of direct entries, not files inside a root-owned subdirectory.
- **Change:** PATH membership no longer escalates; escalation requires a
  directly contained privileged **executable**, whose mode/owner/writability are
  cited as evidence. Nested and non-executable children stay MEDIUM.
- **Regression tests:** unit cases for PATH-only, direct child, nested child,
  non-executable child; FS-004 (HIGH), FS-011/017 (MEDIUM), FS-019 (MEDIUM,
  absent HIGH), INV-001/002.

### 5.4 NULQ-SYS-002: enforcement across modules

- **Original problem:** a permissive SELinux finding set the enforcement flag to
  false, so an enforcing AppArmor module was ignored and "no MAC enforcing" was
  emitted.
- **Evidence:** enforcement must come from each module's state file. LSM-list
  membership only proves a module is advertised. One module's state cannot
  cancel another's.
- **Change:** enforcement is derived from AppArmor enablement and SELinux
  `enforcing`; the generic finding is suppressed by any enforcing module or by
  the specific permissive finding.
- **Regression tests:** mixed AppArmor-enforcing + SELinux-permissive (exactly
  one MEDIUM finding), AppArmor alone (silent), existing missing/permissive/
  enforcing/unknown tests.

### 5.5 Identity memberships

wheel, sudo, admin and root membership moved from MEDIUM to LOW because the
sudo policy is not evaluated. `docker`, `disk`, `lxd`/`lxc`, `libvirt` remain
HIGH; `input` remains MEDIUM. ID-004 now asserts LOW.

### 5.6 Coverage and validator

- Coverage adds `excluded_roots` (deliberate mount exclusions, distinct from
  traversal failures) and `failed_operations` (`operation`, `class`, `message`).
  Cancelled/timed-out rule skips make execution incomplete; missing-observation
  skips remain "not applicable".
- The validator now fails a run on duplicate findings, dangling evidence IDs and
  findings without evidence.

## 6. Evidence and provenance findings

- Every finding is validated before aggregation: ID, rule ID, resource,
  severity, confidence, at least one evidence reference, and explanation are
  mandatory.
- Aggregation rejects evidence IDs that no evidence record defines, merges only
  exact duplicate finding IDs, and sorts deterministically.
- Evidence records carry observation ID, resource, resource kind, collector,
  field, observed value, optional expected value, explanation and collection
  time.
- No finding embeds file contents, environment secrets or credentials. Sysctl
  values, modes, owners, group names and paths are the only observed values.
- JSON, JSONL, Markdown and terminal renderers share the same model, so a
  severity correction propagates to every format.
- Limitation: finding IDs are derived from rule, resource and title, so a title
  change changes the ID. This is documented, deterministic behaviour, not a
  stability promise across rule versions.
- The laboratory's independent integrity check confirms all 46 findings cite
  resolving evidence and that no finding or evidence pair is duplicated.

## 11. JSON schema validation

Schema version remains **1.1**. No release exists and no external consumer was
published, so the two new required coverage fields (`excluded_roots`,
`failed_operations`) are documented as part of the unreleased 1.1 contract
rather than silently changing a shipped version. Backward compatibility:

- additive fields only; no field was removed or re-typed;
- strict consumers that implemented the earlier 1.1 draft would notice the new
  required members, so the change is called out in `CHANGELOG.md` and
  `docs/json-schema.md`;
- future additive optional fields do not require a version bump.

All five reports validate against the published schema under both the Go
validator and Python `jsonschema` (`exit 0`). Stdout remains pure JSON for
`--format json`; diagnostics go to stderr.

## 15. Remaining limitations

- Alpine/BusyBox cannot represent systemd, PAM, SELinux policy, cron or a
  distribution package set; those scenarios are synthetic or unsupported.
- The container shares the Docker Desktop kernel; sysctl and LSM observations
  describe that kernel, not bare metal.
- POSIX ACLs are not evaluated. Writability claims use mode bits, ownership and
  supplementary groups; effective permissions may differ.
- No privileged consumer is observed. PATH and writable-directory findings stop
  at LOW/MEDIUM unless direct replaceability or writability establishes a
  boundary from observed facts alone.
- Sudo policy, `secure_path`, service environments, capabilities, systemd, cron,
  containers and namespaces are not implemented (M3/M4).
- Sysctl baselines are conservative defaults; workload-specific tuning can
  produce LOW deviations that are not vulnerabilities.
- Image identity is not bit-for-bit reproducible: BuildKit attestations and the
  manifest-list digest change across rebuilds. The base image digest is pinned
  and recorded; this is the reproducibility guarantee, not identical image IDs.
- `internal/app` coverage is 22.9%; orchestration is exercised end-to-end by the
  laboratory, but not every error branch has a unit test.
- The repository still has no commit; no release tag exists.

## 16. Outstanding risks

- A LOW PATH finding may understate exposure on a system whose privileged
  automation demonstrably uses that PATH; the tool correctly reports the
  missing evidence rather than guessing.
- MAC profile coverage per service is not assessed; an enforcing module can
  still have permissive or unconfined domains.
- Shared-kernel sysctl findings are contextual and may differ on bare metal.
- Group semantics are documented defaults; site-specific groups (podman socket,
  libvirt configuration) are not inferred.
- The laboratory targets amd64; arm64 builds compile but the Alpine image and
  fixtures were not executed on arm64 in this audit.

## 18. Recommendation for M2

Proceed to **M2 — Linux discovery depth**: process observations, mount-flag
analysis (`nosuid`, `nodev`, `noexec`), ACL-aware permission evaluation and
writable-parent relationships.

For each new rule:

1. state the observation needed to establish the privileged-consumer or
   execution relationship, not only the writable object;
2. add a positive scenario, a negative control and an unavailable-data case;
3. assert severity, confidence and evidence resolution;
4. keep CRITICAL unused unless a relationship is exceptionally severe and fully
   observed.

The M1.5 contract (coverage exclusions, classified failures, validator
integrity) should be reused unchanged.
