## 6. `NULQ-FS-002` HIGH-severity justification

### What the collector observes

For each observed entry: mode, owner UID/user, group, set-owner-ID bits,
execute bits, current-user writability, and the containing directory's mode,
sticky bit, world-write bit and owner. It does **not** observe process
execution, open file handles, service configuration or command consumers.

### What the original rule concluded

Any executable with SUID or SGID directly inside a world-writable non-sticky
directory made the directory HIGH with HIGH confidence. That was wrong for
three separate reasons:

1. **Owner was ignored.** A SUID executable owned by uid 10001, replaced by
   another local user, executes with uid 10001's authority — a delegated
   non-root boundary, not root.
2. **SGID was treated like root SUID.** A root-owned SGID executable grants a
   group, not uid 0; whether that group is privileged is not observed.
3. **Confidence was overstated.** Execution of the replaced binary was never
   observed.

A fourth defect was a false negative: any sticky directory was skipped, even a
`1777` directory owned by the assessed user, who can unlink any entry despite
the sticky bit.

### Corrected condition

HIGH now requires all of:

- the directory accepts entries from other users (`world_writable`);
- the assessed user can remove entries: non-sticky, or sticky and owned by the
  assessed EUID;
- a **root-owned SUID executable** is a direct child (not nested);
- the file has at least one execute bit.

Confidence is MEDIUM. The finding states that replacement would make a later
execution run attacker code as root, and that execution is not observed.

### Is HIGH still defensible?

Yes, with the stated confidence. The observed facts establish the code
injection relationship: root-owned SUID semantics mean execution yields euid 0,
and directory write permission establishes that the assessed user can replace
the entry. The only unobserved link is whether the binary is invoked. That is a
real residual uncertainty, so confidence is MEDIUM rather than HIGH, but the
potential impact (arbitrary code as root from a local account) supports HIGH
severity. Nested files, user-owned SUID, SGID-only and unrelated consumers do
not escalate.

This is an exposure judgment, not a demonstrated exploit. The report, rule
impact and limitations say so.

## 7. Evidence and coverage assessment

- Findings are structurally validated before aggregation; every finding must
  cite at least one evidence ID.
- Aggregation rejects evidence IDs that do not exist, removes exact duplicate
  finding IDs deterministically and sorts findings/evidence.
- The lab validator independently checks duplicate IDs/keys, dangling evidence
  and evidence-free findings; all are zero on the final run.
- Coverage distinguishes execution completeness, traversal completeness,
  permission denials, truncation, unsupported observations, deliberate excluded
  mounts and classified failed operations.
- Deliberate exclusions (`/proc`, `/sys`, runtime/container paths) do not
  downgrade coverage; denials and truncation do.
- Timeout/cancellation classes are carried through executor outcomes; a
  cancelled or timed-out rule makes execution incomplete, while a rule skipped
  for genuinely missing observations remains "not applicable".
- No finding embeds file contents, credentials, environment secrets or command
  output. Observed values are modes, owners, paths, group names, sysctl values
  and LSM state.

Limitation confirmed by source: ACLs are not read, and `writable_by_current_user`
uses mode bits plus the assessed user's groups.

## 8. The finding-count discrepancy

The prior report's explanation was **incorrect**. It said 46 total, 45
asserted, and "one additional sysctl finding". Re-deriving from the manifests
and JSON showed that the 46 figure was coincidental:

- 46 total findings;
- 30 distinct findings matched positive expectations;
- **16** findings were neither asserted nor allowed: 15 `NULQ-SYS-001`
  findings (five each in baseline, fixtures and path) and one
  `NULQ-FS-001` finding for `/usr/lib/lab/standard-suid` in the discovery scan;
- the validator only computed unexpected findings inside a scenario `scope`.
  Those scans had no scope covering the sysctls, and discovery had no
  findings scope at all, so all 16 were silently ignored.

After the corrections and two new `FS-002` fixtures, the honest accounting is:

| Quantity | Value | Meaning |
|---|---|---|
| Total findings | 54 | all five scans |
| Distinct asserted | 38 | matched by positive expectations |
| Explicitly allowed | 16 | 15 kernel-dependent sysctls + one standard-directory inventory in discovery |
| Unaccounted | 0 | neither asserted nor allowed |
| `expected_findings` | 57 | **sum of assertion minima**, including duplicate inventory assertions; not a distinct total |

`expected_findings` is a counter of required matches, not "how many findings
should exist". Comparing it directly with `actual_findings` is invalid. The new
`unaccounted_findings` counter is the meaningful completeness signal.

## 9. Validator correctness

Original weaknesses:

- unexpected findings were only reported inside `scope`; a scan without a
  scope could hide anything;
- duplicate/dangling checks existed but no per-scan accounting tied assertions
  to the complete finding set;
- summary counters could look clean while 16 findings were unaccounted.

Corrections:

- every supported scenario's positive and absence matches contribute to a
  per-scan accounted set;
- `allowed_findings` explicitly accounts for expected-but-unasserted findings
  (kernel-dependent sysctls, discovery's standard SUID inventory);
- any finding left over is reported under `findings.unaccounted` and fails the
  run through `summary.unaccounted_findings`;
- scenario `scope` remains only a localiser for its own unexpected check, not a
  global hiding mechanism.

Regression tests added: `TestUnaccountedFindingFailsWithoutScope`,
`TestAllowedFindingIsAccounted`, plus the existing duplicate/dangling/
evidence-free tests. Final lab result: `unaccounted_findings: 0`.

## 10. JSON schema compatibility

- The repository has no commit and no release; no external 1.1 consumer exists.

## 14. Remaining limitations and risks

- No ACL evaluation; effective permissions may differ from mode-bit inference.
- No observation of privileged consumers, process execution, sudo policy,
  service environments, capabilities, systemd, cron, containers or namespaces.
- FS-002 HIGH remains an exposure judgment: execution of the replaced root SUID
  binary is not observed, only its replacement path.
- Group semantics are conventional and site-configurable; `docker`/`libvirt`/
  `lxd` authority depends on local daemon/socket configuration.
- Sysctl and MAC observations describe the shared Docker kernel; Alpine cannot
  represent SELinux/AppArmor policy or systemd.
- `internal/app` unit coverage is 22.9%; orchestration relies on the lab for
  end-to-end behaviour.
- arm64 was compiled but not executed in the lab.
- Image identity changes across rebuilds; the base digest is pinned, not the
  final manifest digest.
- Repository still has no commit or release.

## 15. Independently verified versus not reproduced

**Verified in this review:** source semantics for all six rules; SUID/FS-002/
PATH/MAC unit behaviour; evidence integrity and duplicate handling; coverage
classification; per-scan finding accounting; schema agreement; both static
builds; full Go gates; five-scan Docker lab twice; isolation probe; cleanup with
an unrelated resource; host-safety state.

**Not reproduced:** bare-metal sysctl behaviour, real SELinux/AppArmor policy
coverage, sudoers authority, docker/libvirt/lxd daemon semantics, ACL-driven
writability, arm64 execution, and any M2+ behaviour. These are explicitly out of
scope or unsupported, not silently assumed.

## 16. Gate decision

No critical security or correctness defect remains. The corrected
implementation no longer reports non-root authority as root exposure, no longer
treats unknown MAC state as disabled, and the validator can no longer silently
ignore unaccounted findings. Remaining items are documented limitations.

Decision: **ACCEPTED** — see `docs/audits/m1.5-final-acceptance.md`.
